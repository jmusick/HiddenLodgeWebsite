# AGENTS.md

Guidance for AI coding agents working in this repository.

## Stack

- **Astro 6** (SSR, `output: "server"`) deployed to **Cloudflare Pages/Workers** via `@astrojs/cloudflare`.
- **D1** (Cloudflare's SQLite) as the database, binding name `DB`. Schema lives as sequential SQL files in `migrations/*.sql` — there is no ORM.
- Pages (file-based routing) live in `src/pages/`. API endpoints are Astro endpoints under `src/pages/api/**/*.ts`, each exporting `POST`/`GET`/etc. and `export const prerender = false`.
- Shared server-side logic lives in `src/lib/**` (plain `.ts`, imported by both pages and API routes).
- Layouts: `src/layouts/Layout.astro` (public site chrome + nav) and `src/layouts/AdminLayout.astro` (admin nav/tabs).

## Conventions

- **Auth checks**: pages check `Astro.locals.isAdmin` / `Astro.locals.isGuildMember` / `Astro.locals.user` and `return Astro.redirect(...)` early if unauthorized. API routes check `context.locals.isAdmin` etc. and return `new Response('Forbidden', { status: 403 })` / `401` early in the handler.
- **Feature flags**: `src/lib/feature-flags.ts` exports `FEATURE_FLAGS`, a plain object of booleans (one per major feature: `rosterTeams`, `raidSignups`, `attendance`, `deathAnalysis`, `mechanicsAnalysis`, `applications`, `feedback`, `tools`, `sim`). A feature that's temporarily disabled but not removed is gated everywhere it surfaces:
  - Nav arrays (`AdminLayout.astro`'s `adminModules`, `Layout.astro`'s `memberNavItems`) conditionally include the entry.
  - Pages add `if (!FEATURE_FLAGS.x) return Astro.redirect('/')` (public) or `return Astro.redirect('/admin')` (admin), placed after the existing auth guard.
  - API routes add `if (!FEATURE_FLAGS.x) return new Response('Not found', { status: 404 })`, placed after the existing auth guard.
  - Flip the flag back to `true` to fully restore a feature — no other code changes needed. Underlying `src/lib/*.ts` business logic and DB schema for disabled features are left intact on purpose.
- **D1 queries**: written as raw SQL via `env.DB.prepare(...).bind(...).all()/.first()/.run()`. `env` is imported from `cloudflare:workers`.
- Migrations are numbered and additive (`NNNN_description.sql`); never edit an already-applied migration — add a new one.
- **Weekly reset / season timestamps**: `src/lib/wow-reset.ts` is the single source of truth for the US weekly reset (Tuesday 11:00 AM America/New_York, DST-aware) and season-start timestamps (e.g. `SEASON_2_START_TIMESTAMP`). This used to be copy-pasted independently in three files with a wrong reset hour — always import from here rather than reimplementing it.

## Commands

- `npm run dev` — Astro dev server + local cron refresher (see `scripts/dev-with-cron.mjs`).
- `npm run build` — `astro build` then patches the Wrangler config. Note: this does **not** run a full typecheck (no `astro check` in the build pipeline) — run `npx astro check` separately if you need one; the repo currently has some pre-existing type errors that build doesn't catch.
- `npm run db:migrate:local` / `db:migrate:prod` — apply migrations. Destructive migrations (DROP/DELETE/TRUNCATE/`ALTER TABLE ... DROP COLUMN`) are blocked unless the file has a `-- allow-destructive` annotation; `npm run db:check:migrations` verifies this plus migration numbering/state without touching a database.
- `npm run db:copy-prod` — copies all production D1 data into your local D1 (schema intersection only; skips `sessions`, system tables, and by default `roster_cache_meta`/`site_settings`). Requires `wrangler` to be authenticated (`npx wrangler whoami`) and a bootstrapped local schema (`npm run db:bootstrap:local`). Safe to rerun — it clears local rows (FK-dependency order) before reinserting. Set `COPY_PROD_INCLUDE_SEEDED=1` in the environment to also copy the normally-skipped seeded tables.

## Notes

- **Cron**: the site is a Cloudflare Pages project, which has no cron triggers, so there is no `[triggers] crons` entry and no `scheduled()` handler. cron-job.org calls the endpoints with an `X-Cron-Secret` header and aborts each request at 30s. Production runs three jobs: `/api/cron/refresh?skipRaiders=1&skipLogs=1` (roster, gear icons, professions/trinkets/attendance when their flags are on), `/api/cron/refresh-raiders`, and `/api/cron/refresh-logs` (raid-log activity + death analysis, then mechanics analysis). Each leg must fit inside 30s on its own: take a deadline at the start, check it before starting each new unit of work, carry the remainder over to the next tick, and cap every upstream request (`AbortSignal.timeout(8_000)` in `blizzard-fetch.ts`, `raider-io.ts`, `wcl.ts`, `raid-log-activity.ts`). When adding a slow leg, give it its own endpoint plus a `skip*` flag on `/api/cron/refresh` instead of adding it to the shared request.
- **Recent-raider filter**: `src/lib/raid-log-activity.ts` syncs "who showed up in a Hidden Lodge Warcraft Logs report lately" straight from the guild's WCL report list (guild 781707) and stores it in `raider_log_activity`. It is deliberately independent of `src/lib/attendance.ts` — that pipeline is tied to scheduled raids and stays empty while `FEATURE_FLAGS.attendance` is off — and so it is **not** gated on that flag. `/raiders` and `/raiders/gear-summary` default to the last `RECENT_LOG_WINDOW_DAYS` (30) and offer a "Show all raiders" toggle; with no synced data both pages fail open and show everyone. `raid_log_reports_seen` is the don't-refetch cursor, so a caught-up refresh costs one GraphQL call.
- **Death Analysis (Season 2)**: `src/lib/death-analysis.ts` backs `/death-analysis` (Tools menu, guild members) and `/admin/log-matching` (admins + officers), gated on `FEATURE_FLAGS.deathAnalysis`. It pulls the WCL guild report list directly — no dependency on `raid_signups`/`primary_raid_schedules` — and keeps reports in The Venomous Abyss that overlap a Thu/Fri 9pm–midnight ET window (DST-aware via `easternWallClockToUtcSeconds` in `wow-reset.ts`), counting only Heroic/Mythic pulls over a rolling 90 days. One report counts per night (`night_key` = ET date): officer override from `death_analysis_night_overrides`, else most qualifying pulls. The sync runs from `/api/cron/refresh-logs`, a few reports per run, and stops starting new reports once its 12s budget is spent. The old `attendance` pipeline (`src/lib/attendance.ts`, `raid_attendance_*` tables) is retired and stays off; don't wire new work into it.
- **Mechanics Analysis**: `src/lib/mechanics-analysis.ts` backs `/mechanics-analysis` (Tools menu, guild members), gated on `FEATURE_FLAGS.mechanicsAnalysis` **and** `deathAnalysis`. It adds no report discovery of its own: it syncs only the canonical per-night reports from `getDeathAnalysisNights`. Bosses and mechanics are declared in `MECHANICS_BOSSES` (WCL encounter id plus debuff ability id). The first is Coiled Altar (3429) with Volatile Venom (1282419), where one `applydebuff` is one orb carried. `mechanics_analysis_reports` is a per (report, mechanic) cursor, so adding a mechanic backfills it. Player role comes from the CombatantInfo `specID` (`ROLE_BY_SPEC_ID`), so a new spec needs an entry there. The sync runs chained after death analysis in `/api/cron/refresh-logs`, with its own 6s budget, and is skipped if death analysis ran past 16s.
- **Warcraft Logs client**: `src/lib/wcl.ts` holds the shared WCL code — OAuth token, `queryWcl`, the rate-limit backoff (shared `site_settings` key), WCL-actor → roster-character matching (`loadWclCharacterLookup` + `matchWclActorCharId`, which trusts the actor's `gameID` — the Blizzard character id — when it's a known character and only falls back to name + realm; name-only matching mis-attributed stats when a deleted character's name was reused), and `fetchReportFightStats` (per-report presence + 4-death-capped death stats, scoped by a caller-supplied fight filter). Both `attendance.ts` and `death-analysis.ts` import from it. `raid-log-activity.ts` still has its own small token/query copy.
- **Useful Links page**: `/links` renders bookmarks tagged `wow` from the Tagstash public API (`src/lib/bookmarks.ts`, profile `JD`), cached 10 minutes at the Cloudflare edge. Links are curated in Tagstash, not in this repo — there is no admin CRUD and no D1 table behind the page (migration `0072` dropped `links`/`link_categories`). Filter chips are derived from each bookmark's other tags minus `NOISE_TAGS`.
- **Articles page**: `/articles` and the homepage's "Latest Articles" feed render posts tagged `world-of-warcraft` from a public Orboro.net API (`src/lib/orboro-posts.ts`, `GET https://orboro.net/api/posts/by-category/[slug]`), same fetch/cache shape as `bookmarks.ts` (10-minute edge cache). Content is authored and hosted entirely on Orboro.net — this repo has no article markdown, no content collection, and no D1 table for it. `/articles/:slug` doesn't render a post; it 301-redirects to the matching post's `url` from that same feed (rewrites to `/404` if the slug isn't found). Both pages carry a small credit link back to orboro.net — keep it if you touch that markup, per the guild's agreement with Orboro.
- A separate companion app (`HiddenLodgeDesktop`, different repo) consumes some of these API routes (e.g. `src/pages/api/desktop/raid-signups-today.ts`) — check before removing/gating an endpoint under `api/desktop/`.
